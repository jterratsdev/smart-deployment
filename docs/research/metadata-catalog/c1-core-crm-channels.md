## Method and status contract

The table order is fixed by priority, then implementation dependency within each priority. `catalogKey` is the stable join and deduplication key. A catalog key is
`<apiVersion>|<deploymentChannel>|<vendorType>`. The profiles are setup-agents
`3.15.0-rc` rules in `.codex/`. When an API version does not apply, the first
segment is `n/a`; the second segment remains the actual deployment channel.

Capability codes are:

- `P`: proven by an exact repository symbol and focused fixture/test evidence.
- `Pt`: partial; some behavior exists, but the catalog row is not end-to-end proven.
- `A`: absent.
- `NA`: not applicable to this deployment channel.

The compact support column is `D/P/X/O/L`: discovery, parser, dependency,
ordering, and post-deploy/provider lifecycle. A type is not "supported" merely
because it appears in `MetadataType` or `DEPLOYMENT_ORDER`.

## Ownership and interpretation rules

1. C1 is the canonical owner for `CustomObject`, its source-format children,
   `Flow`, `PermissionSet`, shared security/UI types, and all aliases in this
   report. C1 also owns shared platform settings such as
   `OrderManagementSettings`; product clusters reference these rows rather
   than copying them.
2. `Account`, `Opportunity`, `Case`, `WorkOrder`, `ServiceAppointment`,
   `MessagingSession`, and namespaced `FSL__*__c` API names are CustomObject
   contents or records. They are not metadata type candidates.
3. A managed namespace is an attribute of an artifact. It does not create a new
   metadata type.
4. Salesforce `SlackApp` and a Slack platform/Bolt app manifest are distinct
   rows because their channels, secrets, deployment tools, and lifecycle differ.
5. `ExperienceBundle` and `DigitalExperienceBundle` are distinct vendor types.
   Aura and LWR site source must not be merged through an alias.
6. Current gap-analysis labels are evidence, not truth. Its hardcoded
   `SCANNER_SUPPORTED_TYPES`, `SOURCE_DIRECTORY_TYPES`, and suffix title-casing
   can disagree with the actual scanner and vendor names.

## Exact cross-cutting gaps

- The stable public `MetadataType` union has 81 ordered names, while the gap
  analyzer hardcodes 26 scanner-supported names. Neither records aliases,
  channels, API version, lifecycle, fixtures, or confidence.
- Source-format composite children under `objects/` are discovered as
  `CustomObject`; individual parsed children are not emitted as graph nodes.
- Graph IDs are inconsistent. Several scanners emit plain object, field, Flow,
  or Apex names while other scanners emit `Type:Name`.
- Parser richness is lost at scanner boundaries, especially Flow and
  CustomObject. This makes dependency support materially weaker than parser
  unit coverage suggests.
- Generic suffix title-casing cannot determine Salesforce manifest names,
  composite/container names, aliases, or case-sensitive folder conventions.
- Experience lifecycle support is path-triggered and incomplete. There is no
  general metadata-type-to-publish contract.
- No lifecycle adapter exists for Field Service managed data, Salesforce
  `SlackApp` secret handling, or external Slack/Bolt deployments.
- Current product rules are setup-agents `3.15.0-rc`; Experience guidance that
  navigation menus are "not metadata" conflicts with the current coverage
  report and must be org-validated.

## Recommended implementation slices

1. **P0 capability registry and aliases.** Add a typed, API-versioned registry
   for vendor type, internal type, aliases, channel, source shape, capability
   evidence, and lifecycle owner. Derive gap status from it. Seed
   `ApexPage`, `ApexComponent`, `CustomApplication`, `CustomMetadata`, and the
   `MatchingRules` decision.
2. **P0 typed graph normalization.** Introduce one node-ID builder and project
   all Flow, CustomObject, PermissionSet, Profile, Layout, and FlexiPage
   references through it. Preserve hard/soft provenance.
3. **P1 CustomObject child expansion.** Emit deterministic components for
   `CustomField`, `RecordType`, `BusinessProcess`, `ValidationRule`,
   `CompactLayout`, `ListView`, and `CustomPageWebLink` while retaining the
   parent aggregate. Avoid double deployment by marking source ownership.
4. **P1 security and CRM rules.** Add focused scanners/parsers for
   `CustomPermission`, `PermissionSetGroup`, `MutingPermissionSet`,
   `SharingRules`, `QuickAction`, `AssignmentRules`, `AutoResponseRules`,
   `EscalationRules`, `DuplicateRule`, and the validated matching-rule vendor
   type.
5. **P1 Experience split.** Implement separate `ExperienceBundle` and
   `DigitalExperienceBundle` path strategies, then make publish planning consume
   catalog lifecycle metadata rather than a single regex.
6. **P1 licensed-provider boundary.** Add read-only detection contracts for FSL,
   Messaging, Territory2, and Salesforce `SlackApp`. Keep automation blocked
   until org/provider evidence proves secrets, activation, and rollback.
7. **P2 nearby families.** Add Service/Omni, Path/Forecasting, Experience config,
   branding, and Field Service settings in small registry/scanner slices.

No slice should add branches to `metadata-scanner-service.ts`; extend focused
scanner registries and parsers instead.

## Limitations

- No `.setup-agents/references/` cache was present. This report therefore uses
  current official Salesforce pages directly and records the cache gap.
- The unversioned coverage report reflects the current Salesforce documentation
  on `2026-07-23`; per-org availability still varies by edition, license,
  feature setting, package version, and namespace.
- Documentation can establish that a type is exposed through Metadata API. It
  cannot prove retrieval completeness, deployment ordering, activation,
  publish, rollback, or secret round-tripping.
- No Salesforce org, Field Service package, Experience site, or Slack workspace
  was mutated or validated during this research.
- Repository inspection was intentionally limited to the metadata contracts,
  scanner/parser/dependency surfaces, gap analyzer, ordering/wave policy,
  lifecycle planner, and their focused tests. No source or test file was
  changed.

## Architectural concerns

### Inherited

The architecture handoff's recommendation to build one typed capability
registry is consistent with the existing scanner-registry direction. The
correction is that provider-owned classification must not be inferred from name
patterns: `DigitalExperienceBundle` and Salesforce `SlackApp` are Metadata API
types with additional lifecycle/security constraints, while an external Slack
manifest and FSL managed records are genuinely different channels.

### Self-imposed

None. This report proposes catalog/scanner/dependency/lifecycle implementation
slices only. It introduces no Salesforce custom fields, objects, labels,
permission sets, or Flows.
