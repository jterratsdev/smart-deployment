# Staged CustomObject FlexiPage Activation

- Task: `SD-OBJECT-FLEXIPAGE-ACTIVATION-PLAN`
- Status: architecture proposal only; not an executable deployment path
- Scope: `CustomObject.actionOverrides` with `type=Flexipage` and a nonempty `content` referencing a `FlexiPage`

## Problem and invariant

The object scanner now records `CustomObject:<object> -> FlexiPage:<page>` from a Flexipage action override. `CustomObject` is in deployment stage 1 and `FlexiPage` in stage 6, so the wave builder correctly rejects the edge. A record page can itself reference the object; adding another graph edge or changing priorities cannot express creation and later activation of _the same object file_. The current `WaveManifestService` emits type/member manifests, and `DeploymentRunner` deploys them against the original source. A manifest that lists the object first would still deploy its override too early. This is a lifecycle operation, not an ordinary single-component dependency.

### CDF Tour plan failure report

Read-only reproduction with `sf smart-deployment plan explain --source-path /Users/jterrats/dev/cdf-sf-org --json` returned CLI `status: 1` and `Deployment-order conflict: CustomObject:cgcloud__Tour__c (stage 1) depends on FlexiPage:CDF_Tour_Record_Page (stage 6)`. This is **not evidence of a graph cycle**: `WaveBuilder.validateDeploymentOrderContracts` rejects a later-stage dependency before topological wave placement. The source object has `View` Large and Small Flexipage overrides whose `content` is `CDF_Tour_Record_Page`; the page itself declares `sobjectType` as `cgcloud__Tour__c`. The object's dependency on the page is real for the _activated override_, but must not force the entire object definition to deploy after its record page. The scanner currently attaches the page reference to the indivisible `CustomObject` node, which makes a single-pass plan fail closed.

Report classification: **valid source reference, invalid single-phase deployment model**, not a spurious parsed name. Do not silence the edge or reorder stages: manifests currently deploy the original object XML including the override. The needed fix is a staged, verified object-foundation → page → override-activation operation with isolated source payloads and persisted resume state as described below. Target-org preexistence for this project is unverified; no CDF metadata was deployed. The isolated activation fixture described later in this document has not yet passed its post-activation metadata comparison, so this report does not authorize that executor.

### Pure object overlay prototype (2026-10-22)

`src/deployment/object-flexipage-overlay.ts` now prepares a foundation XML by removing only selected, validated Flexipage `actionOverrides` from a `CustomObject`; its activation output is the unmodified input XML. It rejects invalid XML, unexpected roots/namespaces, missing page selections, incomplete overrides and duplicate selected action/form-factor pairs. This is a pure transformation, not an operation scheduler or a deployable artifact. Deterministic tests cover mixed overrides, unrelated child metadata and attributes, malformed input and duplicate selections. A read-only local check on the CDF Tour source (9,156 bytes) yielded a foundation of 8,445 bytes with zero `CDF_Tour_Record_Page` content references, while activation was byte-for-byte identical to the source and retained both references. No CDF files or org were changed.

Do not wire this prototype to manifests yet: it does not confirm target object/page existence, decide which source children to deploy, compare effective target overrides, bind overlay hashes into persisted state, reconcile in-flight jobs, or implement no-replay resume. A valid XML transformation alone cannot make `start` safe or make `plan explain` report an executable plan.

### Non-executable operation contract (2026-10-22)

`src/deployment/object-flexipage-operation-plan.ts` represents distinct `foundation:CustomObject:<name>`, `page:FlexiPage:<name>`, and `activation:CustomObject:<name>` operations with explicit `after` barriers and SHA-256 hashes of the foundation XML, each page source, and original activation XML. All requested page sources must exist and have a valid FlexiPage root/namespace; target observation distinguishes unknown and existing objects. It **always** returns `ready: false`: neither a caller-provided observation nor a valid file is enough to authorize deployment. Deterministic tests check new and existing objects, missing observation/source, and a two-page barrier. This contract does not yet own generated files, know whether page contents are deployable in the target org, observe actual target state itself, or persist operation state. The existing ordinary wave path remains fail-closed.

### Advisory resume guard (2026-10-22)

`src/deployment/object-flexipage-resume-guard.ts` now evaluates a proposed persisted operation state against the operation-plan fingerprint and exact target org ID. It requires fresh matching observations for every verified predecessor, checks operation-set consistency and prerequisite order, and blocks started jobs (including jobs with unknown ID), pending operations with remote job IDs, unknown/mismatched observations, and changed plans. It returns only the next **candidate** operation, not authorization to deploy. Its observations are caller-supplied; no Salesforce read, job reconciliation, durable state write, or execution hook exists yet. Deterministic tests cover verified/pending/started states, drift, missing entries and out-of-order completion. `start` and `resume` continue to fail on the original stage conflict; no CDF metadata was deployed.

No source file in the Salesforce project may be rewritten. No live org mutation is authorized by this design.

## Proposed phases

1. **Preflight (read only).** Parse each override, resolve the page by canonical `FlexiPage:<content>` identity, and inventory other object/page dependencies and ignored or missing files. Observe the target object's and page's current existence and relevant override state; failed auth, ambiguous results, absent prerequisites, or unverified inventory block the plan. Do not infer org existence from a missing local file. Decide separately whether the object foundation needs deployment, whether the page needs deployment, and whether an override actually changes. Existing objects must not be overwritten with a stripped source merely to satisfy a graph constraint.
2. **Object foundation (conditional, not authorized).** When an object is new or has independently approved schema changes, a candidate isolated source overlay would omit only the Flexipage overrides scheduled for activation. Preserve every other XML element, namespace, attribute, override, and child metadata unchanged in the candidate. This describes a fixture to validate, not evidence that deploying it preserves omitted target settings. Reject ambiguous formats or any unsupported override type instead of doing a string replacement. Stage only the object foundation and its proven prerequisites; never use the original object member in an earlier general wave. Confirm the deployed foundation before proceeding. For an existing object, especially a standard object, do not deploy a stripped source unless its exact effects on existing settings and overrides have been demonstrated and approved.
3. **Page.** Deploy the exact locally resolved FlexiPage in a subsequent isolated step, after verified object availability and its own dependency prerequisites. Verify the page in the target org after deployment; a successful CLI response alone is not proof of activation readiness. A page absent locally may only be treated as external after positive target-org observation, not by graph omission.
4. **Override activation (conditional, not authorized).** A candidate isolated object overlay would contain the desired final overrides only after page verification. Do not assume omitted fields or other overrides survive a partial standard-object customization. Require a demonstrated preservation strategy and an independent post-deploy observation of the intended override (action name, content, form factor and type) and unchanged unrelated settings. A failed, inaccessible, or contradictory observation pauses without reporting success.

For multiple objects/pages, construct a DAG of typed operations (`foundation`, `page`, `activation`) with explicit `after` barriers; deduplicate shared pages but retain distinct object activations. If a page needs another unverified reference, block rather than assuming the stage number makes it safe. No wave merger may combine operations across a barrier.

## Artifact and resume contract

- Generated overlays belong under a per-run `.smart-deployment/` directory, not under `force-app`; they are ignored by source scanning. Paths must be confined to that directory. The original source bytes remain untouched. A manifest-only transformation is insufficient because `sf project deploy start --manifest` reads the original files.
- Persist a versioned operation plan, exact source and generated-overlay hashes, target org identity, page and override identities, preflight observations, per-operation status, CLI job IDs, verification evidence, and the next operation index. Bind all of these to the plan fingerprint. Existing `createDeploymentPlanFingerprint` covers wave numbers, component IDs and source fingerprint, but not overlays or target observations; it cannot be reused unchanged for this workflow.
- Before each operation and on resume, revalidate source/overlay hashes, target identity, prerequisites and observed target state. On an interrupted CLI job, reconcile the job ID and verify its effect before deciding whether to retry. Never replay a completed object or page operation on the basis of a local cursor alone. If the target diverged or the operation's outcome is unknown, pause for inspection.
- Keep rollback explicit and non-destructive: retain preflight observations and generated artifacts for review, but do not automatically restore prior object metadata or remove newly deployed pages. Object updates can have other consumers; a compensating deployment requires separately verified scope and approval.

## Delivery slices and acceptance signals

1. Add pure preflight and operation-plan types in a focused deployment module, with fixtures for a new object, existing standard object, shared pages, missing or ignored page, and a page referencing its object. The planner must not authorize execution when org observations are unavailable. Preserve the current fail-closed wave conflict until a complete executor is wired.
2. Add deterministic XML overlay generation and byte/hash verification without mutating project sources. Test namespaces, multiple form factors, duplicate overrides, unrelated overrides and mixed object child metadata. Verify the generated source via the same source-format resolver used by the deployment runner; a package manifest alone is not sufficient.
3. Integrate isolated operations with the runner and persisted state, including interrupted jobs, source changes, target drift, no-replay resume, and post-deploy observations. Define migration of existing checkpoint state or reject this new plan on older state explicitly. Test that ordinary deployments cannot bypass a staged override barrier.
4. Only after deterministic tests and independent review, use an explicitly approved disposable org to validate create/page/activate, interrupted resume, and cleanup. Keep CDF and other real projects read-only until the target-org prerequisites and all remaining unresolved references are verified.

## Evidence and open risks

The existing read-only CDF plan rejects `CustomObject:cgcloud__Tour__c (stage 1) -> FlexiPage:CDF_Tour_Record_Page (stage 6)`. This establishes a planning conflict, not the state of the target org. The `gdm-experience` sample contains a `View` override on `Account` pointing to `Account_Lightning_Page` for Large and Small form factors; neither source presence nor successful parse proves deployment safety. Other graph gaps and unplaced nodes remain separate blockers.

### Documentation verdict (2026-10-20)

- **Not established:** The accessible [Metadata API CustomObject reference](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_customobject.htm), [deploy reference](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_deploy.htm), and [action override reference](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/actionoverride.htm) did not provide verifiable text demonstrating that omission of `actionOverrides` in a partial file-based `CustomObject` deployment preserves existing target overrides, or that omission leaves unrelated standard-object settings unchanged. The pages returned a documentation shell in this research environment. This is an evidence gap, not a claim that Salesforce always deletes omitted elements.
- **Candidate observation, not sufficient proof of effective UI behavior:** [Metadata API `readMetadata`](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_readMetadata.htm) or a read-only [retrieve](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_retrieve.htm) of `CustomObject` could supply an object/override snapshot for before/after comparison. An [internal investigation](https://salesforce-internal.slack.com/archives/C0841QK8KU0/p1783088114005829) reports that `read(CustomObject)` surfaced overrides in an installed-package org but flattened them to `Default` in a scratch-org/local-namespace case even though REST describe retained a page identity. A [separate reported standard-object access discrepancy](https://salesforce-internal.slack.com/archives/C023RCPQYNL/p1737383231763699) further cautions against treating a failed or incomplete read as absence. Neither report defines a generally reliable effective-override endpoint.
- **Operational restriction:** No executable overlay (foundation or activation) is authorized for an existing object, particularly a standard object, on these sources alone. Before enabling it, obtain a version-specific, authoritative contract for omission/update behavior or explicitly approved isolated-org before/after evidence covering selected and unrelated overrides, non-override object settings, both form factors, and default behavior. Establish a read-only effective-override observation with permission/error handling and reconcile it with a fresh metadata snapshot; disagreement or unknown is a block, not success. Do not use internal support-only permissions or direct table mutation as a product verification path. Run deterministic fixtures and independent QA before any executor integration.

### Isolated cg-demo observation (2026-10-20)

With explicit approval, `test/e2e/live-isolated-flexipage-override.e2e.test.ts` used only a randomly named `SD_FlexProbe_*__c` custom object and its `SD_FlexProbe_*_Page` record page on `cg-demo` (org `00Dak0000189OhPEAU`). The test confirmed both names absent, deployed the object and page separately, set `View` Flexipage overrides for Large and Small, and retrieved the object as a baseline. It then deployed an object source file with **no `actionOverrides` elements** and a changed label. A second retrieve included the changed label and both original overrides. The live command passed (1 test); independent post-run Tooling API queries for both probe prefixes returned zero records. Two earlier fixture attempts failed before the omission step (invalid page structure and invalid absolute retrieve destination); each fixture was independently confirmed absent before retrying. No existing object or page was edited.

This is evidence of omission preserving two overrides in one custom-object scenario at API 67.0, as observed through source retrieval. It does **not** prove semantics for standard objects, other override types or unrelated settings, or effective Lightning UI assignment. It does not validate the proposed activation overlay, staged executor or no-replay resume. Keep those paths and the existing wave conflict blocked pending their own evidence and independent QA.

### Changed Account overlay and restoration (2026-10-21)

With the user's approval for `cg-demo` as a disposable demo org, a fresh Metadata API 67.0 `Account` snapshot had object XML SHA-256 `6fc801bd2055bdd6c163315a36d87642796f5a8634c51be586ed01a849a253fa`. Two minimal Metadata API packages were prepared under `.smart-deployment/`: the change set `account-changed-probe` assigned the existing `Account_Layout` as the default compact layout instead of `SYSTEM`, and `account-changed-probe-restore` assigned `SYSTEM`. Both packages contained only `CustomObject:Account`, with **no `actionOverrides`**, and both passed `--dry-run` (jobs `0Afak00000p5PbVCAU` and `0Afak00000p5Py5CAE`).

The change deployment succeeded (job `0Afak00000p5Q7lCAE`). Comparing the entire retrieved `Account.object` against the baseline showed exactly one XML line changed: the top-level `<compactLayoutAssignment>SYSTEM</compactLayoutAssignment>` became `Account_Layout`. Both retrieved `View` Flexipage overrides were unchanged, and independent REST describe still returned the same LARGE and SMALL `View` page ID `0M0ak00000GcBNqCAN` (`Account_Record_Page1`). The restore deployment succeeded (job `0Afak00000p5QPVCA2`); the freshly retrieved full object XML was byte-for-byte identical to the baseline (same SHA-256), with the same REST describe overrides and page resolution. No other component was deployed by these packages.

This establishes **one real, reversible property update** on the standard object `Account` in this org in which omitting `actionOverrides` preserved both observed overrides and other retrievable object metadata. It does not prove that omitting overrides always preserves implicit defaults, that an activation overlay can safely add/change overrides, or that per-app/profile page assignments and UI behavior match these observations. Do not unblock the staged executor or extend this result to other orgs without separately tested activation, drift handling, and independent QA.
