## Black-box fixture detail

Built a disposable SFDX project (registered via `sf setup-agents scratch register`, now deleted)
containing: a valid `Account` object + field, a valid `Account.matchingRule-meta.xml` (1 active
rule, `Email__c`), an empty `Contact.matchingRule-meta.xml`, a malformed singular-root
`Lead.matchingRule-meta.xml` (`<MatchingRule>` instead of `<MatchingRules>`), a `DuplicateRule`
referencing the local matching rule (`Account.DupRule1`), one referencing a rule name absent from
the local container (`Account.MissingRuleRef`), and one referencing a standard object with no local
container (`Case.StandardRef`). All CLI invocations ran fully offline (`--source-path`, no
`--target-org`), confirming:

- the malformed file never becomes a component (scan error only), and independently makes
  `MatchingRules` report `unsupported` in `metadata gaps` even with 2 other valid containers present
  (the exact F2 regression scenario, re-verified against the real CLI rather than the security
  reviewer's probe scripts against `lib/`);
- the local-missing reference is a blocking scan error, not merely a fact;
- the target-unknown reference produces no dependency edge and no error, and stays visible in
  `facts.references` (confirmed in the `plan explain` JSON component list);
- neither `MatchingRules` nor `DuplicateRule` ever appears in a generated core manifest — `plan
explain`'s `core-metadata` provider decision is `blocked`, not `included`, whenever either type is
  present, regardless of whether scan errors exist;
- `ci-publish --no-dry-run` reports "blocked before any command ran" and lists every plan error,
  matching `docs/known-limitations.md`'s description exactly.

A second, error-free fixture (also offline, also cleaned up) confirmed the `target-unknown` and
`supported` outcomes hold independently of any scan error being present.

## Regression: C4 OmniStudio and the all-or-nothing behavior change

`special-deployment-plan.test.ts`'s "OmniStudio channel classification (AC-001..AC-004)" describe
block is untouched by the C1-RULES diff and still passes (`classifies native-looking OmniStudio
paths...`, `never generates an executable VBT job placeholder...`, `admits no DataPack record into
the core metadata manifest...`, `skips the OmniStudio phase with no errors...`). The `blocked`
channel classification (`unknown-shape`, `identity-unproven`, `channel-conflict`) in
`omnistudio-channel-classifier.test.ts` is unaffected — the C1-RULES diff touches only
`wave-manifest-service.ts`, `special-deployment-plan.ts` (the new guard integration points),
`special-deployment-executor.ts`, and `ci-publish.ts`, none of which are part of the classifier.

`special-deployment-executor.test.ts`'s "refuses to run any command when the plan already failed
(AC-004, security review F1)" and "...even if success was left true" are the direct regression tests
for the all-or-nothing executor change. `docs/known-limitations.md`'s "`ci-publish` Coordinated
Execution Is All-Or-Nothing" section accurately describes this: before the F1 fix, an OmniStudio
`blocked` classification was reported but the core phase still ran; now any provider's phase error
(OmniStudio `blocked`, AI-evaluation precheck, or the data-quality guard) stops every phase. The
black-box run above independently confirms this for the data-quality guard case specifically. I did
not independently re-run an OmniStudio-`blocked`-plus-clean-core-metadata fixture through the real
CLI (the unit test already covers it and doing so was out of this phase's fixture scope), so this
regression claim rests on reading `special-deployment-executor.ts`'s unconditional early-return
(`plan.success === false || plan.errors.length > 0` blocks every phase, with no per-provider
carve-out) plus the existing passing unit tests — not an additional black-box probe.
